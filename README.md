# Philomena Reverse Image Search Inference Toolkit

## Setup

1. Install necessary dependencies

- python >= 3.12, python-pip
- ffmpeg-dev or ffmpeg-devel
- librsvg2-dev or librsvg2-devel
- rsvg-convert and [safe-rsvg-convert](https://github.com/philomena-dev/philomena/blob/master/docker/app/safe-rsvg-convert)
- [mediatools](https://github.com/philomena-dev/mediatools)

2. Install Poetry

- `pip install pip poetry wheel setuptools -U`

3. Setup repository for inference

- Clone this repository
- Run `poetry install`
- Run `poetry run python hf/compile_transformers_vision_model.py` to download model weights from Hugging Face (346 MB) and generate the JIT model

The generated JIT model, `dinov2-with-registers-base.pt`, will also be required by Philomena when the model is set up there. You can use the copy generated by this script, or allow it to automatically fetch from the GitHub release.

## Option 1 of 2: Acquiring images from a CDN

The toolkit does not assume that you have the image files locally available on the same storage for inference, and provides a method for fetching them. If you _do_ have them available locally, you should [import the image pathnames directly](#option-2-of-2-importing-local-image-paths) instead.

Before proceeding with this step, you will need to generate a CSV file without headers which contains the following columns:

1. The image ID
2. The remote URL where the image ID can be found
3. The path to write the file to

Example rows for the CSV file:

```
1,https://examplecdn.net/img/view/2020/4/24/1.jpg,2020/4/24/1.jpg
2,https://examplecdn.net/img/view/2020/4/24/2.png,2020/4/24/2.png
```

To import the CSV file into the database, run `poetry run python ris/acquire.py load --file images.csv --database index.db`. This will create the database if it doesn't exist yet.

Then, begin downloading the images with `poetry run python ris/acquire.py download --concurrency 16 --database index.db --base-path /path/to/change/to`, where `--concurrency` is a configurable argument controlling how many threads will be used to download, and `--base-path` is an optional argument which changes the directory of relative paths.

The download process is **resumable**: if it is interrupted, simply restarting the download command will resume downloading.

To generate the CSV file, you can use something like the following `psql` command against the main database. Replace the CDN URL with your own, and collapse it to a single line:

```sql
\copy (
    select
        i.id,
        (case when i.hidden_from_users
            then concat('https://examplecdn.net/img/', to_char(i.created_at, 'YYYY/fmMM/fmDD/'), i.id, '-', i.hidden_image_key, '/full.', i.image_format)
            else concat('https://examplecdn.net/img/view/', to_char(i.created_at, 'YYYY/fmMM/fmDD/'), i.id, '.', i.image_format) end),
        concat(to_char(i.created_at, 'YYYY/fmMM/fmDD/'), i.id, '.', i.image_format)
    from images i
    where i.destroyed_content = 'f'
) to 'images.csv' with (format csv);
```

## Option 2 of 2: Importing local image paths

If you have images available locally to the machine you plan to run inference on, generate a CSV file without headers which contains the following columns:

1. The image ID
2. The path the file can be found at

Example rows for the CSV file:

```
1,2020/4/24/1.jpg
2,2020/4/24/2.png
```

To import the CSV file into the database, run `poetry run python ris/acquire.py local --file images.csv --database index.db`. This will create the database if it doesn't exist yet.

To generate the CSV file, you can use something like the following `psql` command against the main database. Be sure to collapse it to a single line before pasting:

```sql
\copy (
    select
        i.id,
        (case when i.hidden_from_users
            then concat(to_char(i.created_at, 'YYYY/fmMM/fmDD/'), i.id, '-', i.hidden_image_key, '.', i.image_format)
            else concat(to_char(i.created_at, 'YYYY/fmMM/fmDD/'), i.id, '.', i.image_format) end)
    from images i
    where i.destroyed_content = 'f'
) to 'images.csv' with (format csv);
```

## Running batch inference

All batch inference jobs are **resumable**: if a job crashes or is otherwise interrupted, simply restarting the command will allow it to pick up where it left off with no loss of data integrity.

Image files which are unreadable due to corruption are automatically marked and not retried on resume.

### CUDA

Run `poetry run python ris/infer.py batch --model-path $PWD/dinov2-with-registers-base.pt --device cuda --concurrency 16 --pixels 16588800 --database index.db --base-path /path/to/change/to`

This will use 16 CPU threads to decode images with a total canvas pixel count less than 16.5MP, and then serially feed them into the CUDA device. This provides excellent device utilization (above 90%) and is the most efficient way to infer.

### CPU

Run `poetry run python ris/infer.py batch --model-path $PWD/dinov2-with-registers-base.pt --device cpu --concurrency 2 --pixels 1073741824 --database index.db --base-path /path/to/change/to`

This will use 2 CPU threads to decode images with any total canvas pixel count Philomena supports, and process them in parallel. These images bottleneck on CPU decoding, so it is generally more efficient to completely process them on the CPU. This is used for processing the remaining images which are too large to efficiently infer using CUDA.

## Exporting feature vectors

Run `poetry run python ris/extract.py binary --database index.db --output features.bin`. This file is a binary for small size and fast generation--generating JSON lines can take over 20 minutes, but generating the binary file only takes a few seconds. This binary can be imported by Philomena using the provided release task.

## General notes

It is fine if the images are on rotational or otherwise slow media. However, the database file should be on solid state storage _if at all possible_; it should only only grow to be a few gigabytes large, and it will be unnecessarily slow to use the toolkit otherwise.

## Why is this project written in Python when the "real" inference code is written in Rust?

Both the Rust code in Philomena and Python code in this repository use the same PyTorch model, while the Rust code uses libtorch to execute it. However, PyTorch does not optimize model execution graphs when used from its C++ API.

The result of this is that in the Rust code, every single thread must wait for each individual step in the model (like a matrix multiplication) to complete before submitting the next step, which results in huge latency surrounding model submissions. In contrast, the Python code does not suffer from this deficiency and submits the entire execution graph to the GPU at once, giving extremely fast command submission. For processing millions of images, this is a practical necessity.
